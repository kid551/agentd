1. 一句话结论

做成一个树外 bundle 包 dsh-superagent，装进 ~/.dsh/profiles/desktop。它带一个宿主插件（奏折存储、状态机、派工、事件路由、批处理注入、Watchdog）、两个 agent preset（superagent-router、superagent-worker），以及一个 dsh.client 浏览器侧（奏折主面板、会话行徽标、输入框上方的 band）。

Router 和 Worker 都是 dsh 的原生根会话，由插件用 ctx.agents.create() 创建。不再有外部守护进程、HTTP、MCP 壳和 CLI 对账。

2. 需要你拍板的决策

每条都给出推荐和理由。绿色为推荐项。

D1 · Worker 的形态：根会话 还是 Router 的子会话（subagent）

根会话（ctx.agents.create，不设 parentAgent）子会话（ctx.subagents.startActivation）
在侧栏可见是，归入对应项目的 Workspace（需 workspaceRegistry.attachSession）否，只能从 Router 的标题栏目录进入
每个 Worker 自己的 cwd / 模型 / preset都可以（meta.cwd、agentOptions、setup 里 mount preset）preset 可以；cwd 默认继承父会话
向用户提问 / 请求审批可以，走 dsh 原生界面不行：子会话的审批会被自动拒绝，提问被拒（DELEGATED_CALLER）
并发上限插件自己定每棵树 8 个（maxActiveSubagents）
和父会话通信插件自己做（followup / steer / inject）现成的完成通知与 sendMessage

推荐根会话。子会话不能提问、不能请求审批，这一条就足以排除：Worker 卡在审批上正是 agentd 最大的痛点（偏差 36–41）。

D2 · 「单聊」= 直接切到 Worker 会话里说话

agentd 的单聊是在 Router 输入框里截流，再把话转给 Worker。这样做是因为 Worker 在 VSCode 里不好打开，而且转达的话审查不认（偏差 41）。dsh 里这两个前提都不存在了：

  1. Worker 是侧栏里的普通会话，ctx.uiWorkspace.openSession(id) 一步就能打开。
  2. 你在 Worker 会话里打的字就是那个会话里的用户消息，审批天然认可。
  3. dsh 也没有通用的提交前钩子，只能截 / 和 @ 开头的行。硬截流要么替换整个输入框，要么监听 DOM 按键，都很脆弱。

推荐：单聊就是打开 Worker 会话。Worker 会话的输入框上方挂一条 band，写着「单聊 #12 · 返回 Router」。插件监听 Worker 会话里的 user/message，往 Router 里 inject 一行「你对 #12 说了…」，只补上下文、不唤醒 Router，保持 Router 的全局记忆完整。

保留一个轻量通道：在 Router 里打 @12 内容，由 inputTriggers 认领后，以 queue 方式发给 #12。这适合不想切换会话的短指令。

已定（2026-11-04）：单聊 = 切到 Worker 会话，加 @12 短指令。

D3 · 提问与审批：原生处理，只做镜像

Worker 用 dsh 原生的提问工具和审批弹窗。插件在 Worker 的 agentCtx 上挂 user-questions/request 和 approval/request 的 waterfall 监听，只观察、调用 next() 放行：把奏折标成 asking，往 Router 推一条事件，在面板和侧栏行上亮黄点。你可以点进 Worker 原地回答，也可以让 Router 转述后在单聊里答。

推荐只做镜像、不拦截。agentd 的整套 PermissionDenied、PreToolUse、grant 标记文件、批准词判定（偏差 36–39）都可以删掉。代价是答题必须进 Worker 会话，不能在 Router 里一句话替它批准。这一点是故意的：Router 模型不应该能替你批准。

备选：拦截后改由 Router 代答（waterfall 支持直接返回答案）。只用于普通提问，审批永远不代答。

已定（2026-11-04）：原生处理，插件只做镜像。

D4 · 奏折存储：dsh 的 storage-domain（JSON） 还是 自带 SQLite

dsh 给插件的正规存储是 ctx.storageDomain.open(defineDomain(...))：落在 ~/.dsh/storages，同步读、持久写，变更时发 domain/changed。dsh 没有给插件用的 SQLite 服务。自己用 node:sqlite 能跑，但不在支持范围内，HMR 卸载时还得自己管连接。

推荐 storage-domain。量级是几百张奏折、几千条事件，不需要索引和 SQL。状态机迁移的原子性改用「单写者 + 内存串行队列」保证：只有宿主插件写，所有迁移经过同一个 apply()。事件表要设上限，超出的旧事件归档到 spill。

D5 · 执行器范围：只派 dsh Worker，还是也能派 Claude Code Worker

「放开思路」的一个方向：dsh 的 Router 作为唯一入口，Worker 定义成一个可替换的 executor seam。

  • dsh：dsh 原生根会话，用 DeepSeek 或其他已配置的模型。
  • claude：把奏折转交给 agentd 守护进程的 HTTP API，由它起 claude --bg。agentd 降级为「Claude Code 执行器适配层」，Router 层整体搬到 dsh。

已定（2026-11-04）：v1 只派 dsh 原生 Worker，executor 字段与接口留口，agentd 保持独立。

D6 · 应用退出时 Worker 怎么办

Worker 跑在桌面应用的宿主进程里，应用一关它们就停了。会话日志会保留，可以冷恢复。HMR 重载插件也会销毁插件创建的 agent（见 spike S2）。

推荐：重启后把 working / asking 的奏折标为 interrupted（新状态），不自动续跑。面板给出「恢复」按钮，语义同 agentd 偏差 46：先只读自查、汇报、提问，回答之前不做写操作。理由：被打断的 Worker 可能停在一次部署中途。

已定（2026-11-04）：标 interrupted，等你点恢复。

备选（未采用）：自动恢复 working 的奏折。要「一直在线」，应该把同一个 bundle 装进 headless 或 web profile，常驻跑在另一台机器上（第 6 节 §5），而不是让桌面应用自作主张。

D7 · 模型

实施偏差（2026-11-04）：v1 里 Router 和 Worker 都用你当前的默认模型，见 implementation-notes「dsh-superagent」偏差 1。

Router 用轻模型（你当前默认的 deepseek-flash），Worker 用最强的可用模型，两者都可以在 bundle 配置里改。用 agentOptions 按会话指定模型。不要用 sessionController.selectModel()：它会顺手把你的全局默认模型改掉。

D8 · 代码放哪

已定（2026-11-04）：放在 agentd monorepo，新增 packages/dsh-superagent。纯逻辑先复制过来移植，v2 接 agentd 时再抽成 packages/core 共享。

4. 数据模型与类型接口

4.1 存储（storage-domain superagent，version 1）

tickets: {
  id: number                 // 自增，界面显示 #id
  title: string
  task: string               // 任务原文
  executor: 'dsh'            // D5 留口：'claude'
  projectPath: string        // 真实路径
  workspaceId?: string       // dsh Workspace
  sessionId?: string         // Worker 会话；创建前为空
  worktree?: string
  model: { provider: string; model: string; reasoningEffort?: string }
  state: TicketState
  pending?: { kind: 'question' | 'approval'; summary: string; at: number }
  lastReport?: string
  createdAt: number; endedAt?: number
}
events: {                     // 只追加；上限 N 条/奏折，超出归档
  id: number; ticketId: number
  kind: 'dispatched' | 'progress' | 'ask' | 'approval' | 'answered' | 'user-said'
      | 'ready' | 'blocked' | 'failed' | 'stalled' | 'interrupted' | 'resumed'
      | 'message' | 'closed' | 'stopped'
  body: string; actor: 'router' | 'worker' | 'user' | 'superagent'; at: number
  routerSeen: boolean         // 是否已批量注入 Router
}
meta: { routerSessionId?: string; lastEventId: number }

4.2 状态机（沿用 agentd state.ts，增删两处）

状态变化
queued / working / asking / ready / blocked / failed / done / stopped保留，含义同 agentd。
interrupted新增（D6）：应用退出或 HMR 重载时，处于 working/asking 的奏折进入此状态；resume 后回到 working。
asking含义变化：由原生提问/审批的 waterfall 观察进入；用户在 Worker 会话里回答后，监听到 answered 退出。不再有「问题表」和撤回逻辑，问题本身由 dsh 管。

4.3 宿主服务 ctx.superAgent（preset 行通过 inject 取得）

interface SuperAgent {
  dispatch(input: { title: string; task: string; project: string; worktree?: boolean }): Promise<Ticket>
  message(id: number, text: string): Promise<void>       // Router → Worker：idle 则 followup，否则 steer
  stop(id: number): Promise<void>
  retry(id: number): Promise<void>                        // blocked/failed
  resume(id: number): Promise<void>                       // stopped/interrupted
  close(id: number): Promise<void>                        // 收：dispose Worker agent，保留会话
  list(filter?: TicketFilter): Ticket[]
  read(id: number, depth: 'summary' | 'events' | 'transcript'): Promise<string>   // 链式召回
  projects(query?: string): Project[]
  // Worker 侧（worker preset 的工具调用）
  report(sessionId: string, text: string): void
  done(sessionId: string, outcome: 'ready' | 'blocked' | 'failed' | 'dropped', text: string): void
}

5. 架构

DeepSeek Harness 宿主进程（desktop profile）
├─ bundle: dsh-superagent
│  ├─ host plugin  superagent           → 提供 ctx.superAgent
│  │   store      storage-domain「superagent」（单写者）
│  │   dispatcher ctx.agents.create({ meta:{cwd}, agentOptions, setup: mount worker preset })
│  │              + workspaceRegistry.create(path).attachSession(id)
│  │   observer   ctx.on('session/event') · agent/status · approval/request · user-questions/request
│  │              （只看 Worker 会话，按 sessionId → ticket 映射）
│  │   batcher    需人处理的事件入队 → Router 空闲且 1.5s 无新事件 → 一条 followup；忙则 inject
│  │   watchdog   setInterval 3s：idle 且未 done → stalled；漏投递复查；启动时 interrupted 对账
│  │   projection sessionProjections.register('superagent') 挂在 Router 会话上（S3 不通则改 ws 路由）
│  ├─ preset  superagent-router   persona + Router 工具，无执行工具
│  ├─ preset  superagent-worker   standard 的副本 + report/done + Worker 规则 persona
│  └─ client  dsh.client          面板 · 行徽标 · band · /next · @12 认领
└─ dsh 原生：会话日志、侧栏、审批弹窗、提问卡片、冷恢复、compaction

5.1 一次派工的关键路径

  1. Router 调 dispatch → store 写 queued（同步）。
  2. 检查同项目占用与并发上限（同步，读内存）。
  3. await ctx.agents.create(...)：必须等。拿到 sessionId 后才能做映射和挂 Workspace。
  4. workspaceRegistry.create(path) 与「写 working + sessionId」可以并发；attachSession 等前者。
  5. agent.followup(任务文本)，立即返回给 Router。

关键路径上只有两次串行等待：创建 agent（第 3 步，后续都依赖 sessionId），以及 attachSession（依赖 workspaceId）。其余全部并发或同步完成。

5.2 一次提问的往返

  1. Worker 调原生提问工具 → user-questions/request waterfall → 插件观察：奏折进入 asking，记一条 ask 事件，然后 next() 放行。
  2. dsh 在 Worker 会话里画出提问卡片，侧栏行亮黄点（原生行为加插件徽标）。
  3. batcher 把「#12 问：…（附此前最后一条进展）」注入 Router，Router 转述给你。
  4. 你点「单聊」或 /next 进入 Worker 会话，原地回答 → 插件观察到回答，奏折回到 working，往 Router inject 一行「你已回答 #12」。

6. PDF 六个模块在 dsh 里的落地

PDFdsh 里的做法分期
§2 双层架构Router = 无执行工具的根会话（轻模型）；Worker = 各项目目录里的根会话（强模型）。作用域用 preset 加 agentCtx.tools.restrict 实现，比 agentd 用钩子拦截更硬。P1
§2.1 批处理batcher：Router idle 时 followup 一条合并消息；running 时 inject，下一步自动带上。agent/status 事件代替 agentd 的 2 秒轮询。P1
§3.1 两级过滤Source 插件（GitHub 用 gh 轮询 PR、评论、CI；本地 git hook；日程）→ 程序层规则（来源、仓库、作者白名单）→ 候选事件给 Router 做语义判断。P3
§3.2 订阅直通新增 threads 表（如 github:owner/repo#123）。Worker 派出时订阅，同 Thread 的后续事件直接 steer 给 Worker，Router 只收一行 inject。P3
§3.3 Inline & Spill / 链式召回事件 ≤300 字加奏折头，交回类事件附此前最后一条进展（agentd 偏差 45）。read 三跳：summary → events → transcript。transcript 用 ctx.sessionQuery.readSession，长内容存 ctx.spillStore。不用原生 session_query 工具：它要求 cwd 完全一致，跨项目读不了。P1 / P2
§3.4 投机执行候选事件（如 issue、CI 红）在规则命中时静默派一张 speculative 奏折：只复现、只在 worktree 里改。有结果才通知 Router，否则悄悄关掉。P4
§4.1 异步 ReActdsh 原生已支持：Worker 的 tool-jobs，Router 侧的派工本身就是异步的。现成
§4.2 多信道v1 只有 dsh 界面。P3 的 GitHub Source 同时作为输出信道：Router 按「PR 结构化、IM ≤100 字」的规范回写。P3
§5 存算分离 / BYOM同一个 bundle 装进 headless 或 web profile，常驻跑在一台开发机上；桌面应用通过 web 访问。更远一步：仿照 e2b 的 fs-* 加 subprocess-* provider，写一个连到端侧 daemon 的执行世界。P5（探索）
§6 Watchdog两层。程序层是 watchdog 定时器（stalled、漏投递、对账），P1 就有。LLM 层是一个独立的 Watchdog 会话，用 ctx.schedule 每 N 分钟唤醒，读所有 working 奏折的最近动作，判断是否原地打转或偏离目标，必要时 message 纠偏或通知 Router。P1 / P4

7. 相对 agentd：哪些绕法不再需要

agentd 的绕法原因dsh 里
守护进程 + HTTP + 自举/过期/重启（偏差 12、16、27、42）Claude Code 会话不在同一个进程插件就在宿主进程里，删除
Worker 侧 MCP 壳（偏差 6、7）只能通过 MCP 给 Worker 加工具agentCtx.tools.register，删除
claude agents 对账、pid 判存活（偏差 1、21）拿不到会话句柄AgentHandle 加 agent/status，删除
transcript 全目录搜索（偏差 3、44）日志位置不可推算sessionQuery / session/event，删除
权限钩子、grant、批准词（偏差 36–41）auto 审查只认会话内的用户消息原生审批加镜像（D3），删除
单聊截流、/say 重启注入（偏差 31、41）Worker 不好打开，转达的话不被认可直接打开 Worker 会话（D2），删除
iTerm2 attach（偏差 34、43）VSCode 打开会另起一个进程uiWorkspace.openSession，删除
注入被拒就排队（偏差 4）引擎拒绝插件开新回合followup 总能唤醒，仍保留补投逻辑以防竞态（见 S5）

保留并移植：状态机、同项目串行、收即停、恢复与重试的区分、Inline 摘要加局部性、链式召回、压缩后重发总览（dsh 有 compaction 事件）、项目扫描去重、band 语义色。

8. 风险与必须先做的 spike

S2 是能否成立的关键：dsh-agent README 写着 handle.dispose() 会「stops the loop, unregisters, removes the session」，而 HMR 重载或卸载插件时会销毁插件创建的 agent。要先弄清「remove」是只从内存注册表里移除，还是会删掉持久化的日志。如果会删日志，Worker 就不能由插件持有，改为 ctx.sessionController.create() 创建（会话归 controller 所有、跟 UI 新建会话一样）。那样一来，模型要靠 preset 固定，还得核实 preset 能不能指定模型。
编号验证什么不成立时的退路
S1profile 插件 ctx.agents.create({meta:{cwd}}) 加 attachSession 后，会话出现在对应 Workspace，能打开、能继续对话；重启应用后仍在，能冷恢复。改用 sessionController.create({cwd, workspaceId, agentPreset})
S2dispose 和 HMR 是否删除会话日志（见上）；重载后能否用 sessionController.resolveAgent(id) 重新拿到 Worker。同 S1
S3第三方插件能否往 Router 会话 append 自定义事件类型并注册 projection（会话不变量：「模型可见即已记录」）。面板改走 webServer.registerUpgrade 的 ws 推送（dsh-better-sidebar 的做法），并加 origin 校验
S4在 Worker 的 agentCtx 上 prepend 的 approval/request / user-questions/request 监听，只观察加 next() 时，原生 UI 是否照常工作；能否观察到「已回答」。改为轮询 dsh 的「待交互」状态（侧栏黄点的数据源）
S5agent 正在退回 idle 时到达的 steer/inject 是否会搁浅（tool-jobs README 有记载）。watchdog 每 3 秒复查：agent idle 但 inbox 非空，或有未送达事件，就补发 followup
S6preset 行能否 inject 宿主插件提供的 ctx.superAgent；Router preset 去掉 shell/fs 后是否仍能正常启动（有没有隐式依赖）。工具改在 setup 里注册，不进 preset
接口稳定性：dsh 是 0.2.1-rc.5 nightly，preset 刚从目录改成插件行，setup 签名也刚改过。bundle 要锁定一个 dsh 版本区间，启动时检查所需服务是否存在，缺了就明说，不要静默降级。

10. 机械部分（这部分你可以放心交给我）

  1. 包结构：packages/dsh-superagent/，内含 package.json（dsh.bundle.patch + dsh.client）、cordis.patch.yml（插入 host 插件和两个 preset 行）、src/host/*、src/client/*、presets/*。纯逻辑（状态机、摘要、批处理决策）放在包内的 src/core/，不依赖 dsh，单测覆盖；v2 时再上提为 packages/core。
  2. 构建：tsdown 出 host ESM 和 client 的 Module Loader 格式，React 等从 loader 的 require 取，不打包进来。TypeScript、prettier（无分号）、eslint。
  3. 样式偏差：你默认要 tailwind，但 dsh 规定插件 UI 用 CSS Modules 加 --dsw-alias-* 主题 token，不许用字面颜色。为了和明暗主题一致，这里遵守 dsh 的规定，记入偏差。
  4. 测试：core 用 vitest 单测。host 用 dsh 的 test-support 起最小组合（mock LLM）做集成测试：派工 → report → done → Router 收到批量事件。client 只测纯函数（分组、配色、band 文案）。
  5. 安装：开发期在 ~/.dsh/profiles/desktop/cordis.patch.yml 里 insert 本地路径，打开 HMR root 指向源码目录。稳定后用 dsh plugin --profile desktop add <路径> 装成 bundle。卸载只需删掉这一层。
  6. 文档：README.html 增加 dsh 一节；implementation-notes.md 增加「dsh」小节，记 spike 结论与偏差。
