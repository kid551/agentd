Super-agent 并行派工（定稿，已实现）

2026-11-04 · 初稿经 agentd-6c 审核，13 条意见全部采纳后重写 · agentd 守护进程、router-mod、dsh-superagent 三处都已实现 · 实现细节与偏差见 implementation-notes.md「并行派工」一节

0. 前提（用户已定）

  1. 加只读奏折：不占项目，也不被占用拦住。
  2. 写入奏折每张开一个 worktree，从最新 origin/main 拉分支，通过 MR 回到 main，互不等待。
  3. Worker 做完先交回；你点「开 MR」它才 commit / push。
  4. 验收完成后清理这张奏折的 worktree 和本地分支。

1. 和初稿不同、你最可能要调整的决策

只读奏折没用 plan 模式（实测推翻了初稿 D4）。后台会话里，plan 模式碰到 Write 不是拒绝，而是弹权限确认。agentd 自己的 report 工具也弹，加了放行钩子还是弹。没人能点，Worker 就卡住。改成 auto 模式并拿掉 Edit / Write / NotebookEdit，Bash 只靠规则约束。按你的决定，只读奏折仍然不占项目。残余风险：只读 Worker 违规用 Bash 写，正好撞上同目录的写入 Worker。
D1 交付方式按项目路径配置，默认 local。~/.agentd/config.json 加 
"projects": { "~/code/Acme/acme": { "delivery": "mr" } }
用路径作 key：出现同名仓库时项目 id 会变，用 id 配置会悄悄失效。Router 的 worktree 参数去掉了：mr 项目的写入奏折一定开 worktree，local 项目一定在主目录。这行配置还没写进你的 config.json，要你点头。
D2 合入即结束，自动停 Worker、自动清理。合入不听 Worker 自报，守护进程自己用 git ls-remote 核对：origin 上这个分支已被删掉才算合入。acme 是压缩合并，看 main 的历史判断不了；自动合并脚本合入时会删源分支。
D3 合入前「收」= 放弃，不限状态。有 worktree 的奏折，不管在哪个状态，收都要带 discard=true，面板是「放弃」按钮、点第二下确认。删 worktree 和分支，删前把提交存进 refs/trash/<分支>。dropped 也直接删。停（stop）不清理，因为之后还能恢复。
D5 位置与命名。<项目>/.claude/worktrees/agentd-<id>-<戳>，分支 agentd/<id>-<戳>，戳是奏折创建时间（36 进制）。dsh 用 superagent 前缀。两个宿主各自从 1 编号、库重置后编号重来，都不会撞名。不忽略 .claude/ 的项目，会在仓库本地的 .git/info/exclude 加一行，不进版本库。

3. 状态机：不加新状态（审核第 3 条）

working ──done(ready)──▶ ready「待审」──open_mr──▶ working「MR 中」(mrOpened) ──done(merged)──▶ done → 停 Worker、清理
   report / ask / answer / stalled / retry / resume 在 MR 阶段照常，mrOpened 不变
任何有 worktree 的状态 ──close(discard)──▶ done → 停 Worker、强制清理

5. 你会看到的

  • acme 的几张写入奏折同时起，最多 4 张（maxConcurrent）。
  • 卡片上多了「只读」或「⎇ 分支名」标签；「待审」卡片的按钮是「开 MR」和「放弃」。
  • 「MR 中」卡片显示 Worker 最近的动作；合入后奏折自动进入已结束，事件里写着清理了什么。

6. Worker 规则 3（三种，lane-rules.ts）

  • 只读：不改任何文件、不做有副作用的操作；没有写文件的工具，Bash 只跑只读命令。
  • MR：分支名；不碰项目主目录（包括项目文档要求在主工作树做的对齐和 reset）；依赖自己准备。a 段做完不 commit、done(ready)；收到「开 MR」进入 b 段：commit、push、开 MR 并设删除源分支，自动合并脚本放后台跑、前台定期查看（单次等待不超过 5 分钟），只动自己的 MR，不直接推 main、不晋级，合入后 done(merged)。
  • local：不变。

7. 实测结论

#结论
S1plan 模式不可用（见第 1 节）。auto 模式加拿掉写工具，用真守护进程跑完一张只读奏折：读文件、跑 git log、report、done，全程不用人。
S2未实测：Worker 在 worktree 里能否用项目自带的 MR 命令行工具查 MR。工具若按绝对路径读主目录的配置，从 worktree 调用应当一样。第一张真 MR 奏折时留意。
S3守护进程自己 fetch 并建 worktree，基于 origin/main，不基于本地 HEAD（有测试）。带子模块的 worktree 删除要加 --force（git 2.55 实测）。
信任已信任仓库的 worktree 能直接起（acme 实测）；从未被信任的仓库报未信任，父目录被信任也不算。
端到端一次性仓库：两张 MR 奏折同时建好 worktree；不带 discard 的收被拒；带 discard 的收删掉 worktree 和分支，提交留在 refs/trash/。

8. 遗留与风险

  • 冲突推迟到合入时：后合入的那张要 rebase，语义冲突时 Worker 用 ask 问你。
  • 有的项目 main 每进一个提交都会取消正在跑的流水线：Router 提示词要求它建议你把纯文档的小改动并进已有的 MR 奏折，不单独开 MR。
  • 规则 3 和项目文档冲突：AGENTS.md 让 Agent 帮别人的 MR rebase、合并后在主工作树 reset，规则 3 都禁止。第一次并行时留意 Worker 听的是哪边。
  • dsh 的只读奏折只有规则约束，照旧占用 local 项目（偏差 P2）。
  • 旧方案留下的 worktree 不归新清理逻辑管，要手动处理。refs/trash/ 不会自动清。
